# Check strength and flakiness

## 1. The questions

Forge trusts a repository's declared checks completely: if they pass after the agent exits the branch is pushed, so verification is exactly as strong as the checks, and Forge cannot tell whether a suite would catch a wrong change. Question (a): how do teams measure whether a suite is strong enough to trust, and is mutation testing a practical gate for repos of a few thousand lines? Question (b): what do CI systems do when the same commit yields different check outcomes on different runs, and what should Forge do when a check fails once?

## 2. Check strength

**What mutation testing measures.** A mutation tool inserts one small fault at a time (flip `>` to `>=`, delete a statement, swap `+` for `-`) and reruns the tests; a mutant no test fails on has survived. Mutation score is killed / (killed + survived). Google calls it "widely considered the strongest test criterion" and notes coverage "might be misleading, as in many cases where statements are covered but their consequences not asserted upon" ([Petrović and Ivanković 2018](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/46584.pdf)). The strongest evidence against coverage as a proxy is Inozemtseva and Holmes: 31,000 generated suites over five Java systems up to 724 KSLOC, effectiveness measured by mutants killed; with suite size controlled, correlation "typically ranges from low to moderate", so coverage "should not be used as a quality target" ([ICSE 2014](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf)).

**Cost at Forge's scale.** Cost is viable mutants times (incremental build + test time), since cargo-mutants runs both "once per viable mutant" ([performance](https://mutants.rs/performance.html)). Measured on the Forge 2 tree (5,258 lines of Rust, `cargo test` in 2.5 s): 380 mutants; a 1/10 shard ran 38 in 63 s with `-j 2` (19 caught, 16 missed, 2 unviable, 1 timeout), so a full run is about 10 minutes and the sampled score is 54%. The multiplier is the suite's runtime, so a 60 s suite on the same code would take hours. Diff scoping cuts this: cargo-mutants `--in-diff` "tests only mutants that overlap with regions changed in the diff", though edits can "cause code in a different region or a different file to no longer be well tested" ([in-diff](https://mutants.rs/in-diff.html)); StrykerJS `--incremental` reused 3,731 of 3,965 results in its announcement example ([Stryker blog](https://stryker-mutator.io/blog/announcing-incremental-mode/)).

**Tooling per language.**
- TypeScript/Vitest: StrykerJS has a Vitest runner since v7.0; it forces `perTest` coverage and bails on the first failing test; no browser mode ([vitest runner](https://stryker-mutator.io/docs/stryker-js/vitest-runner/)). Thresholds default `{high: 80, low: 60, break: null}`; below `break` exits 1 ([configuration](https://stryker-mutator.io/docs/stryker-js/configuration/)). Mature.
- Rust: cargo-mutants needs no config, requires hermetic tests, times out at 5x baseline (min 20 s), and its documented CI workflow "will fail if it finds any uncaught mutants": the default gate is zero survivors, not a score ([goals](https://mutants.rs/goals.html), [CI](https://mutants.rs/ci.html)). Mature.
- Go: gremlins is 0.x, "designed to work well on smallish Go modules", admits "a run can take hours" on large ones, and gates with `--threshold-efficacy` (exit 10; KILLED/(KILLED+LIVED)) and `--threshold-mcover` (exit 11), both default 0 ([gremlins](https://github.com/go-gremlins/gremlins), [unleash](https://gremlins.dev/0.4/usage/commands/unleash/)). go-mutesting reports a score but documents no threshold ([go-mutesting](https://github.com/zimmski/go-mutesting)). Usable.
- Python: mutmut 3 mutates function bodies via trampolines, selects tests by stack depth, exports CI stats ([mutmut](https://github.com/boxed/mutmut), [docs](https://mutmut.readthedocs.io/en/latest/index.html)). cosmic-ray offers distributed runs; its gating commands could not be verified (docs page 404) ([cosmic-ray](https://cosmic-ray.readthedocs.io/en/latest/)). Adequate.

**What score is meaningful; what people gate on.** The only large industrial deployment refuses to use a score. Google (17 million mutants, 760,000 changes, 24,000 developers) found it "infeasibly expensive to compute the absolute mutation score" and that the score is "neither concrete nor actionable, and it does not guide testing"; developers initially rated 85% of mutants unproductive, and the system now surfaces a median of 2 mutants per changelist against 460 to 1,734 for traditional mutagenesis ([Practical Mutation Testing at Scale](https://arxiv.org/pdf/2102.11378)). Over six years, exposed developers "write more tests", "fewer mutants survive for new changes over time", and mutants are coupled with real high-priority faults ([ICSE 2021](https://homes.cs.washington.edu/~rjust/publ/mutation_testing_practices_icse_2021.pdf)). Meta's ACH likewise uses mutants as test goals, not scores ([Meta 2025](https://engineering.fb.com/2025/09/30/security/llms-are-the-key-to-mutation-testing-and-better-compliance/)). Open-source gates are tool defaults: Stryker's 60/80 bands, cargo-mutants' no survivors in the diff, gremlins' off-by-default threshold. Claims that "60% is a reasonable start" appear only in blog posts seen in search results (unverified). Equivalent mutants make 100% unreachable, so any absolute threshold is arbitrary; the actionable signal is the survivor list in changed code.

## 3. Flakiness

**Prevalence.** Google's TAP saw 1.6M test failures per day, 73K (4.56%) caused by flaky tests ([Luo et al. 2014](https://mir.cs.illinois.edu/lamyaa/publications/fse14.pdf), citing Google). Google's 2017 post shows flakiness rising with test size, and that when a stable test went flaky after a code change "the problem was a bug in production code 1/6th of the time" ([Google 2017](https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html)); Trunk quotes Google's rates as 0.5% of small, 1.6% of medium, 14% of large tests ([Trunk](https://trunk.io/blog/what-we-learned-from-analyzing-20-2-million-ci-jobs-in-trunk-flaky-tests-part-1)). Meta holds that "all real-world tests are flaky to some extent", with unit-test baselines under 1% and some end-to-end frameworks near 10% ([Meta 2020](https://engineering.fb.com/2020/12/10/developer-tools/probabilistic-flakiness/)); Uber sees about 1,000 flaky of 600K Go tests ([Uber overhaul](https://www.uber.com/en-US/blog/flaky-tests-overhaul/)). At build level, 46.77% of restarted Travis builds flipped fail to pass, so at least 0.80% of all builds were flaky; causes were tests, network, timeouts ([Durieux et al. 2020](https://arxiv.org/pdf/2003.11772)).

**Root causes.** Luo et al., 201 flaky-fix commits in 51 projects: Async Wait 45%, Concurrency 20%, Test Order Dependency 12%, the rest resource leaks, network, time, I/O, randomness, floating point, unordered collections; 78% were flaky from the commit that introduced them ([FSE 2014](https://mir.cs.illinois.edu/lamyaa/publications/fse14.pdf)). pytest adds cleanup failures and global state under parallelism ([pytest](https://docs.pytest.org/en/stable/explanation/flaky.html)).

**Policies in use.** Google reruns a failing test 10 times on the same code and labels it flaky if any rerun passes (Luo, citing Micco). Meta "retries them once" and feeds history into a Bayesian score; flaky tests drop out of change-based selection ([Meta](https://engineering.fb.com/2020/12/10/developer-tools/probabilistic-flakiness/)). Uber calls a test stable only after 100 consecutive passes on main, excludes flaky tests from blocking CI, re-enables after 100 passes, and cut flaky tests by about 85% ([Uber 2021](https://www.uber.com/en-US/blog/handling-flaky-tests-java/)). Bazel's `flaky` attribute reruns up to three times and is "generally discouraged"; `--flaky_test_attempts` marks pass-after-fail as FLAKY ([Bazel](https://bazel.build/reference/be/common-definitions), [flags](https://bazel.build/reference/command-line-reference)). Gradle's test-retry plugin defaults `maxRetries` 0 and `failOnPassedAfterRetry` false ([plugin](https://github.com/gradle/test-retry-gradle-plugin)); Develocity defines FLAKY as "fails and succeeds within the execution of a single" task and says failing the build on it "should be considered carefully" ([Develocity](https://docs.develocity.ai/2026.2/guides/flaky-test-detection-guide/)). GitHub Actions has no automatic retry, only manual same-SHA re-runs ([GitHub](https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-workflow-runs/re-running-workflows-and-jobs)); Buildkite steps retry any non-zero exit twice by default, max 10 ([Buildkite](https://buildkite.com/docs/pipelines/configure/retry)). Quarantine systems define flaky as "the same test is run multiple times on the same commit SHA with different results" and prefer muting (run, soft fail) to skipping so recovery stays observable ([Test Engine](https://buildkite.com/docs/pipelines/configure/tests/flaky-tests), [states](https://buildkite.com/docs/pipelines/configure/tests/test-suites/test-state-and-quarantine)).

**Is "rerun once" sound?** Lam et al. reran Java suites 4,000 times: across 107 flaky tests the median failure rate was under 0.5% (mean 2.7%), and after one failure 87.8% pass within 5 reruns; they judge Google's ten "not well justified" and recommend at most 5 ([Lam et al. 2020](https://mir.cs.illinois.edu/winglam/publications/2020/LamETAL20ISSRE.pdf)). Detection is the expensive direction: tests were still being caught after 10,000 reruns, and rerunning 89,668 tests 2,500 times would cost 1.6 CPU-years ([Parry et al. 2023](https://eprints.whiterose.ac.uk/id/eprint/198846/1/s10664-023-10307-w.pdf)). So one rerun is a cheap, usually correct classifier for a low-rate flake, but it cannot distinguish "flaky test" from "the agent introduced nondeterminism", which Google's 1-in-6 figure says is common.

## 4. Recommendation for Forge

**(a) Measure strength as survivors, not as a score.** Add `forge audit <repo>`: detect the language, run the native tool (cargo-mutants, StrykerJS with the Vitest runner, gremlins, mutmut) over the whole tree with the repo's declared test command, store per-file caught, missed, timeout and unviable counts plus the survivor list in the repo record, and print the score for humans. Do not gate pushes on it: the score is per-repo, thresholds are arbitrary, and Google dropped the metric for that reason. Spend the budget where it changes outcomes: after checks pass on an attempt, run the tool diff-scoped (`--in-diff`, `--incremental`) over the agent's diff and, if any mutant survives, use one retry to hand the agent the survivor lines as test goals (the Google and Meta model); report survivors in the task result either way. Failure modes: non-hermetic or slow suites take hours or time out spuriously, so cap wall time and skip over budget; equivalent mutants cannot be killed, so the retry must be single and never fail the attempt; gremlins and cosmic-ray are less mature, so Go and Python need escape hatches; an agent told to kill mutants can write brittle tests, so survivors are a hint, never a gate.

**(b) Same-commit rerun, then classify, never silently pass.** When check C fails at commit X, Forge reruns only C, once, on the identical commit in a fresh sandbox with no agent turn between; default one rerun, operator-configurable up to 3 (Bazel's ceiling). Record every run: index, exit code, duration, output hash, stderr tail. Two failures: the attempt fails and the agent gets feedback as today. Fail then pass: C's outcome is FLAKY, never PASS, and the rerun does not consume the agent's retry. FLAKY is read against the baseline Forge should already run (checks on X's base commit before the agent starts, kept as history): if C also flaked on the base or in the repo's last 10 recorded runs, it is repo flakiness, so proceed, stamp the push with `flaky_checks`, and after 3 flakes in 10 runs ask the operator a crisp quarantine question; if C was stable before, the change introduced nondeterminism, so do not push and spend one retry telling the agent "C failed once and passed once on your commit" with both outputs. Failure modes: every real failure costs one extra run of that check; a single rerun mislabels a rate-f flake as real with probability about f, small but not zero; order-dependent tests can pass on rerun from a different order and be misread as flake; a flaky base commit masks an agent making it worse; the baseline run adds latency to every task.
