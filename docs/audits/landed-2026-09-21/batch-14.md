# Landed-work audit, batch 14 (forge, tasks 680-694)

This audit checks each task's landed change against its own text. Four of
the landings (680, 684, 688, 690) are `Merge main into …` commits; their
own change was read as `git diff <landed>^2 <landed>`, the second parent
being the branch the merge commit was recording the base into. The other
six (681, 683, 689, 691, 693, 694) landed as plain commits, read as `git
diff <base> <landed>`.

Two of those six needed the base corrected from what the task record
names, because an unrelated branch (a different numbered task) merged in
between the stated base and the landing, taking the literal `git diff
<base> <landed>` far wider than the task's own change:

- **681**'s stated base `1fbf56be7848` does not match `47d7086fbe5c`'s
  actual parent `1973fea0` (itself `Merge the current base into
  forge/679-execution-task-4-of-5`, parents `05586e3d` and `1fbf56be7848`).
  Task 679 (not in this batch) landed its loop-output feature on top of
  `1fbf56be7848` via that merge; 681's own one-file fix sits on top of
  that at `47d7086fbe5c`. Its own change is `git diff 1973fea0
  47d7086fbe5c` (one file, 12 lines), not the 679+681 combination `git
  diff 1fbf56be7848 47d7086fbe5c` (10 files) the stated base would give.
- **688**'s diff is as given (`git diff a574e1928037^2 a574e1928037`); its
  own branch history runs `4990ab2` (the original landing, named by the
  supervisor's answer) → `edcdaab` (merge of main) → `4a941d8` (the one
  fix) → `25a316a` (a lint-driven test-file move) → `a574e192` (merge main
  again). That whole chain is 688's own change and is what is reviewed
  below.

Several pieces have moved since landing: task 680's worker tests moved
from an inline `mod tests` in `src/worker.rs` to `src/worker/tests.rs`;
task 681's `recorded_directive`/`run_directive` moved from `src/job.rs` to
`src/job/directive.rs`; task 684's `relay`/`refuse`/`refused_path` stayed
in `src/egress.rs` but `src/job.rs`'s loop/step logic (unrelated) kept
evolving around them; task 693's `check_worker`'s succession logic moved
from an inline function in `src/doctor.rs` to `src/doctor/succession.rs`,
and `tests/e2e/successor.rs` grew from the one test 693 added to over
twenty by later, unaudited tasks (695+); task 690's `adopt_running_binaries`
gained a lock and a `missing_release_bins` guard, and the commit id it
uses moved from the short to the full sha, both by task 691/693's own
infrastructure changes, not a correction of 690.

Only the tests each task named, or their current successors, were run
(not the full suite), with `bwrap` present at `/usr/bin/bwrap`. All of
them passed on 2026-10-03 against this tree. (Two runs — `forge job test
gc-nightly` for 689 and one upgrade e2e test for 690 — first failed with
"disk full"/"database or disk is full": this machine's `/tmp` is a 1 GiB
tmpfs and these tests copy or build sizeable binaries into scratch
directories under it. Re-run with `TMPDIR` pointed at the real disk, both
passed; this is an environment artifact of this audit run, not a defect
in either task's own change.)
